@AGENTS.md

cmeprep.me — practice questions and timed mock exams for medical board/exit
examinations. Next.js 16 (App Router) + Supabase + Tailwind v4 + shadcn/ui +
PayPal. See [README.md](README.md) for what is and isn't built and the local
setup steps.

## Commands

```bash
npm run dev            # dev server
npm run build          # production build
npm run lint           # eslint
npx vitest run         # all unit tests  (npm test also works)
npx vitest run tests/unit/scoring.test.ts        # one file
npx vitest run -t "partial refund"               # one test by name
npx tsc --noEmit       # typecheck — run this, `next build` alone won't catch everything
npx supabase start     # local stack (needs Docker); prints URL + keys for .env.local
npx supabase db reset  # rebuild local DB from migrations + seed
npx next typegen       # regenerate route types after adding/moving a route
```

Auth emails land in Mailpit at http://127.0.0.1:54324 locally. There is no CI
and no e2e suite — lint, typecheck and vitest are the whole gate.

## Next.js 16 notes

`middleware.ts` is `proxy.ts` (nodejs runtime). `cookies()`, `params` and
`searchParams` are Promises. Route handlers type their second arg as
`RouteContext<"/api/…/[id]">`, generated by `next typegen`. Before writing
anything framework-shaped, read the relevant guide under
`node_modules/next/dist/docs/` — this Next version predates most training data.

## Architecture

### Data model

Taxonomy is `exams → specialties → subjects → questions`, with
`question_options` hanging off questions. Access is sold **per exam**:
`subscriptions.exam_id` scopes a purchase (a `null` exam_id row is
grandfathered all-access). `plans` are the sellable products. Answers in
flight live in `test_answers`; submitted answers become immutable `attempts`
rows that drive accuracy, weak areas and streaks.

Migrations are the source of truth. `lib/supabase/types.ts` is **hand-
maintained** to match them — update it in the same change as a migration.
New tables need explicit grants (see `..._grants.sql`) or every query,
including service-role ones, fails with "permission denied".

### Three Supabase clients — pick deliberately

| module | RLS | use from |
| --- | --- | --- |
| `lib/supabase/server.ts` | enforced | Server Components, Server Actions, route handlers |
| `lib/supabase/client.ts` | enforced | Client Components |
| `lib/supabase/admin.ts` | **bypassed** | route handlers/server libs only, *after* verifying the caller yourself |

`createAdminClient()` is `server-only`. Anything importing it inherits that,
so it can never be pulled into a Client Component.

### Authorization layers

`proxy.ts` only refreshes the auth cookie and does optimistic redirects — it
runs on every prefetch and is deliberately not the authorization layer. Real
enforcement:

1. `app/(app)/layout.tsx` → `requireUser()`; `app/admin/layout.tsx` →
   `requireAdmin()` (both validate the JWT via `getUser()` and load the profile).
2. Route handlers verify the caller before touching the admin client —
   `requireAdminJson()` in `lib/admin/api-auth.ts` returns 401/403 JSON rather
   than redirecting.
3. RLS in Postgres as the backstop.

**Server Actions are not covered by layouts** — a POST to an action runs before
any layout renders. Every action calls `requireUser()`/`requireAdmin()` as its
first statement, outside any try/catch (they signal by throwing `NEXT_REDIRECT`,
which a catch block would swallow). Actions return
`{ error?: string; success?: string } | null` for `useActionState`.

### The `-core` / server split

Modules ending `-core.ts` (`scoring`, `entitlements-core`, `subscriptions-core`,
`payments-core`, `catalog-core`, `reconcile-core`, `admin/import-core`, …) are
pure and unit-tested; their sibling without the suffix imports `server-only`
and does the DB/network work. Put business rules in the core module so vitest
can cover them, and keep each rule stated exactly once — the cores cross-import
rather than restate (e.g. entitlements defers to `isEffectivelyActive`).

### Correctness never reaches the browser mid-test

`question_options` is revoked from client roles; students read
`question_options_public` (no `is_correct`). Only `lib/tests.ts` and
`lib/results.ts` read correctness, and results/review refuse to serve it while
a test is `in_progress`. `lib/scoring.ts` must not be imported by a Client
Component. Multi-correct scoring is all-or-nothing in v1.

### Timing

`tests.expires_at` is set server-side at creation; the client countdown only
corrects for clock skew. Submits past the deadline (+30s grace) are rejected,
and any expired test found on a read path is scored from its staged answers.

### Payments

Flow is create order → capture → grant, with the PayPal webhook covering the
browser-died case. `recordCapturedPurchase()` in `lib/subscriptions.ts` is the
one entry point: it writes the `payments` row **before** attempting the grant,
so money is never lost to an early return; a `payments` row with
`subscription_id` null is exactly what the `pg_cron` sweep at
`/api/cron/reconcile` looks for. Grants are idempotent on the PayPal order id
(capture route and webhook race deliberately). Periods stack per exam.
Partial refunds are recorded, not punished. Money is int cents parsed by
string regex — never `parseFloat`. Known gaps: [payments-backlog.md](payments-backlog.md).

### Admin

All admin mutations go through `audit()` (`lib/admin/audit.ts`) with a typed
action name; bulk operations write one summary row, not one per item. Deletes
are soft (`deleted_at`) so past papers stay intact. The bulk question importer
reduces an .xlsx to a cell matrix at the server boundary
(`lib/admin/import.ts`) and does everything else in `import-core.ts`, so
preview and commit cannot drift; `IMPORT_ROW_CAP`, `CHUNK_SIZE` and the routes'
`maxDuration` must be raised together.

## Conventions

- `@/*` path alias for everything; validation via zod in `lib/validation.ts`,
  using `uuid()` (`z.guid()`) rather than `z.uuid()` — Postgres accepts any
  8-4-4-4-12 hex value.
- Brand tokens (coral/teal/sun/ink/blush), Poppins for headings/wordmark,
  Public Sans for body, defined in `app/globals.css` under Tailwind v4
  `@theme inline`. shadcn components live in `components/ui/` (style
  `radix-nova`) — regenerate via the shadcn CLI rather than editing by hand
  where practical.
- Comments in this codebase explain *why* a non-obvious choice was made
  (usually a bug it prevents). Match that: when changing such code, update the
  comment or explain why the constraint no longer holds.
- Image domains are allow-listed narrowly in `next.config.ts`; adding a remote
  image source means editing `remotePatterns`.
